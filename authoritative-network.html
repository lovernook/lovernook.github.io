02 / NETWORK & STATE

回合制 1v1：重复指令与断线恢复

最难的情况往往不是“消息发不出去”，而是服务端已经执行，客户端却没有收到结果。

lovernook · 2026 年 9 月 28 日 · 基于《一笔江湖》项目复盘

先决定：谁有权改变战斗状态？

《一笔江湖》使用独立 TCP 服务端与两个 Unity 客户端。客户端提交技能和量化轨迹，服务端检查会话、对局、回合、席位、构筑、冷却与能量，再用共享规则重新评分和结算。客户端不提交最终伤害，也不决定胜负。

动画与界面消费结算结果。把伤害放到动画事件中计算，会使动画时长、丢帧与播放失败影响逻辑；权威状态应该先明确，再由表现层呈现。

选择技能 / 画线→ Submit 指令→ 服务端校验与重算→ revision 快照→ 主线程应用→ 动画和 UI

三个标识，解决三个不同的问题

  • commandId 标识一次提交。同一指令重到不能再次扣能量、再次结算。
  • matchId 标识一场对局。上一局的迟到消息不能污染再战后的状态。
  • revision 标识同一对局内的状态版本。客户端不能让旧快照覆盖新快照。

这些标识不能互相代替。例如再战后的新对局 revision 可能更小，所以必须先识别 matchId，再判断版本。简单地拒绝一切较小 revision，会把新对局合法快照也丢掉。

回执丢失时，不能直接再放一次技能

考虑这个时间线：客户端发出 A，服务端执行 A 并推进回合，回执在应用层被模拟丢弃，随后客户端断线。此时界面看起来没有成功，但逻辑已经执行。若重连后创建新 commandId 再发一次，就把“不确定结果”变成了“新的操作”。

当前恢复路径保留待确认指令。重连后查询原指令的结果，并等待权威快照恢复可操作状态。commandId 去重与状态同步一起工作，避免客户端凭本地动画猜测结算是否发生。

连接丢失 → 锁住战斗输入
         → 约 2 秒后尝试恢复会话
         → 查询待确认指令 / 接收权威快照
         → 对齐对局与回合后恢复操作

恢复 token 的有效窗口为 30 秒，保存在服务进程内。断线期间回合倒计时继续；服务端关闭时，客户端不会自行宣布胜利。这也意味着服务端重启恢复并未实现，不能把会话重连等同于持久化容灾。

网络线程与 Unity 主线程的边界

网络线程负责接收、反序列化和排队，不直接触碰 Unity 对象。主线程每帧最多处理 32 条入站消息；队列限制 64 条、单帧消息体限制 64 KiB，服务端还有每连接每秒 10 条消息的限制。这些上限让异常输入有边界，但它们不是吞吐量或并发能力的压测结果。

规则层复用可以减少两端算法漂移，内容摘要帮助发现配置不一致。不过“服务端重算轨迹”只表示不接受客户端自报伤害，无法单独识别脚本生成的完美轨迹，也不能据此声称已完成反作弊。

已有证据与尚未覆盖的范围

阶段 D 的最终包运行过同一台机器上的两个独立客户端，共五局回归，覆盖每方向 0 / 100 / 300 ms 应用层延迟、丢弃一次已受理指令的回执、双方再战和返回房间修改构筑。两端最终状态 JSON 逐局完全一致；网络线程清理有检查记录。

这些测试并不等于两台物理电脑的真人对战，也不等于真实网络层丢包测试。公网部署、NAT、TLS、账号系统、服务端重启恢复、长时间负载仍需分别验证。配置允许的房间数量也不能直接写成“已支持的实测并发”。

复盘问题：为什么 TCP 可靠传输，仍然需要 commandId？

TCP 解决连接内字节流的可靠有序传输，不替应用回答“断线前业务是否已经执行”。应用超时、重连和结果查询仍会产生执行状态不确定的问题，因此需要业务标识与幂等处理。
